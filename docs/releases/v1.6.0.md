# OTYA Player v1.6.0

**Build:** 10  
**Release type:** Production major modernization  
**Platform:** Android  
**Backend:** PeterSmartLink OTYA production services

## Overview

OTYA Player 1.6.0 establishes the new production architecture for the OTYA system. This release replaces legacy app assumptions with real server-backed authentication, production update/configuration services, explicit Google Drive recovery, hardened release signing, offline-first media behavior, and the refreshed OTYA interface.

## Important upgrade notice

This release starts the new OTYA account generation. Legacy application user/account/session/history data is not migrated into the new production system. Users of an older unsupported OTYA/Played generation should register again in the new version.

Local media on the Android device remains local and is not uploaded as part of account creation or Drive recovery.

## Authentication and account security

- Real OTYA backend authentication through `https://petersmartlink.com`.
- Server-issued access and refresh tokens; no fake/local credential sign-in.
- Secure token storage on Android.
- Email verification using the OTYA OTP contract.
- Password-reset flow with session revocation after reset.
- New-device/security alert support.
- User-friendly network/auth errors without raw backend exception leakage.

## Google Sign-In

- Google identity sign-in is supported without Firebase Authentication.
- The Google ID token is verified by the OTYA auth backend.
- The Web OAuth client ID is used consistently as the server audience.
- Basic Google Sign-In requests identity scopes only.
- Google Drive access is not silently granted during sign-in.

## Private Google Drive recovery

- Drive permission is requested only when the user explicitly backs up, restores or deletes a recovery backup.
- Uses the narrow Google Drive App Data scope.
- Recovery snapshots are versioned and validated before restore.
- Google access tokens remain memory-only.
- Raw music/video files are not included.
- OTYA Safe/private media is not included.
- Passwords, OTPs, OTYA JWTs, refresh tokens, API keys and server secrets are excluded.

## Playback and offline-first behavior

- Local playback remains the primary experience and does not require the backend to be online.
- OTYA continues to use a single media engine for audio/video playback.
- Background audio, media controls and Android playback integration remain supported.
- Backend, Google Drive or remote-config failures do not disable normal local playback.

## OTYA Hub and interface

- OTYA Hub uses the production tool layout with a three-column first-nine structure.
- Video Library remains optimized for a one-column media list.
- Theme catalog uses two-column theme cards.
- Remote image themes support `previewUrl`, `wallpaperUrl` and `imageUrl`.
- Downloaded theme assets are stored in OTYA-owned storage for offline use.
- PNG, WebP and JPEG formats are preserved correctly.

## Seasonal themes

- Christmas automation: December 15–26.
- New Year automation: December 27–January 7.
- New Year is reusable and is not hard-coded to a specific year.
- A user's manually selected theme/photo takes precedence over automatic seasonal themes.

## Beam local transfer

- Beam is LAN/Wi-Fi/hotspot based.
- Transfer links use a random per-transfer token.
- Original filenames are preserved.
- Loopback-only transfer addresses are rejected instead of producing unusable QR codes.

## Safe

- Device biometric authentication is supported where available.
- PIN fallback uses secure storage.
- Re-authentication timeout is enforced for sensitive access.
- Private Safe media remains local and is excluded from Drive recovery snapshots.

## Remote control and production backend

OTYA uses the production backend for supported online functions including:

- authentication;
- app configuration;
- feature switches;
- maintenance and update policy;
- announcements;
- online themes;
- release/version metadata;
- feedback and operational services;
- optional cloud/AI integrations.

Remote configuration is designed to fail safely to local cache/default behavior when the network is unavailable.

## Updates and downloads

- Production update checks use the PeterSmartLink backend.
- Release artifacts are published through the hardened GitHub Actions release pipeline.
- arm64 and armeabi-v7a APKs are produced separately.
- SHA-256 verification is generated for release artifacts.
- Production signing fails closed when release signing credentials are unavailable.
- Release artifacts are published to the OTYA Cloudflare R2 release system and GitHub Release as configured by CI.

## Security and CI

- Static analysis and automated tests run in GitHub Actions.
- Security/CodeQL workflow is present.
- Dependabot monitors Flutter, Android/Gradle and GitHub Actions dependencies weekly.
- Production secrets are kept out of Flutter source and repository content.
- Release signing credentials and cloud deployment credentials are supplied through secure CI configuration.

## Backend/email integration

- OTYA backend and auth Worker deployment is managed from GitHub Actions.
- Transactional email uses the verified `petersmartlink.com` Resend configuration through server-side adapters.
- Backend operational alerts have been proven to deliver through Resend.

## Compatibility

OTYA Player v1.6.0 is the supported new-version baseline. Older application generations should not be assumed to share account/session/backend state with this release.

## Release checklist

Before publishing the tag, confirm:

- Debug APK CI is green.
- Security CI is green.
- Production signing secrets are configured.
- `GOOGLE_CLIENT_ID` is configured for the release build.
- Cloudflare R2 release credentials are configured.
- Current production backend deployment is healthy.
- A fresh-user registration/verification/login test succeeds.
- Google Sign-In and explicit Drive recovery are validated on a release-signed build.
